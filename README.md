# git diff
Команда git diff показывает разницу между файлами в разных состояниях. Она подсвечивает, какие строки кода вы добавили (зеленым цветом с плюсом +) или удалили (красным цветом с минусом -).
Зачем нужна: Чтобы проверить себя перед коммитом и точно знать, что именно вы изменили в проекте.

Частые примеры использования:

* __`git diff` — показывает изменения в файлах, которые вы отредактировали, но еще не добавили в индекс (то есть до того, как вы написали git add)__.
* __`git diff --staged (или --cached)` — показывает изменения в файлах, которые вы уже добавили в индекс через git add, но еще не закоммитили.__
* __`git diff имя_ветки1 имя_ветки2` — показывает разницу между двумя ветками целиком (например, git diff main feature).__
* __`git diff ID_коммита1 ID_коммита2` — показывает, что изменилось между двумя конкретными точками в истории.__

# load average
Load Average (средняя загрузка) — это показатель, который отражает среднее количество процессов, находящихся в состоянии ожидания процессора (CPU) или дискового ввода-вывода (I/O) за определенный промежуток времени.
Команда __`top`__ или __`uptime`__ выводит три числа: за 1, 5 и 15 минут.
* Как оценивать: Значение нужно сопоставлять с количеством ядер CPU. Если у вас 4 ядра, то Load Average 4.0 означает, что система загружена ровно на 100%. Если значение выше 4, процессы начинают вставать в очередь, и система может «тормозить».

# inode
Inode (индексный дескриптор) — это специальная структура данных в файловой системе Linux, которая содержит метаданные о файле (размер, владельца, права доступа, даты изменения и указатели на физические блоки диска, где хранятся сами данные).
* Зачем нужны: В Linux имя файла — это лишь ссылка в каталоге, указывающая на номер inode. Сама файловая система работает именно с inode.
* Важное ограничение: Количество inode фиксируется при форматировании диска. Один файл или одна папка = один inode.

# zombie process
Zombie (процесс-зомби) — это процесс, который уже завершил свое выполнение (вызвал __`exit`__), но еще числится в таблице процессов ОС.
• Почему так происходит: Когда процесс умирает, операционная система хранит его код возврата и статус, чтобы родительский процесс (parent) мог их прочитать (с помощью системного вызова __`wait()`__).
• Проблема: Зомби не потребляют ресурсы CPU или оперативную память, но они занимают ID процесса (PID). Если зомби станет слишком много, в системе закончатся свободные PID. Убить зомби командой __`kill -9`__ нельзя (он уже мертв), нужно перезапустить его родительский процесс.

# No space left on device
Ошибка "No space left on device", но место на диске есть.

Самая частая причина этой ситуации — закончились свободные inodes.
Поскольку на каждый файл нужен один inode, если на диске создано огромное количество мелких файлов (например, миллионы файлов сессий или логов), индексные дескрипторы закончатся раньше, чем физическое место на диске.
• Как проверить: Выполните команду __`df -i`__. Она покажет использование inode в процентах. Если там 100%,придется найти и удалить директории с миллионами мелких файлов.

# Linux от включения до логина
1. __`BIOS / UEFI`__ (Инициализация оборудования): При включении питания запускается микропрограмма платы. Она проводит самотестирование (POST), опрашивает оборудование и ищет загрузочное устройство (диск, флешку) согласно приоритету в настройках.
2. Загрузчик (__`GRUB`__): __`BIOS/UEFI`__ передает управление первому сектору диска. Запускается загрузчик (обычно GRUB). Он выводит меню выбора операционной системы (если их несколько) и загружает в оперативную память ядро Linux и временную файловую систему.
3. Ядро (Kernel): Ядро Linux берет управление на себя. Оно инициализирует процессор, память и ключевые драйверы устройств.
4. __`Initramfs / Initrd`__ (Временный корень): Так как реальный жесткий диск может быть зашифрован или находиться на сложном RAID-массиве, ядро сначала монтирует временную файловую систему в оперативной памяти (__initramfs__). Оттуда загружаются необходимые драйверы файловых систем и контроллеров, после чего монтируется уже настоящий корневой раздел (/).
5. Система инициализации (__`Systemd / SysVinit`__): Ядро запускает самый первый процесс в системе с PID 1 (в современных дистрибутивах это почти всегда systemd). Он начинает параллельно или последовательно запускать системные службы (сеть, логирование, графическую оболочку, cron и т.д.) согласно уровням запуска или таргетам.
6. Приглашение в систему (Login): __Systemd__ запускает менеджер дисплея (__GDM/LightDM__ для графики) или службу __agetty__ (для текстовой консоли). На экране появляется окно или строка ввода логина и пароля.

## Основные сигналы

| Номер | Название | Что делает | Описание |
| :--- | :--- | :--- | :--- |
| **1** | `SIGHUP` | Перезапуск | Сообщает процессу, что терминал закрыт. Часто используется для **перезапуска демонов** и перечитывания их конфигов без полной остановки. |

## Иерархия каталогов Linux (FHS)
В Linux все начинается с корневого каталога `/` (root). DevOps-инженеру критически важно знать, где лежат конфигурации, логи и исполняемые файлы.

*   `/bin` и `/sbin` — **Исполняемые файлы**. Здесь находятся базовые системные утилиты (`ls`, `cd`, `mkdir`) и инструменты системного администрирования.
*   `/etc` — **Конфигурация**. Сердце настроек сервера. Тут лежат конфигурационные файлы для Nginx, Docker, SSH и других сервисов.
*   `/var` — **Динамические данные**. Самая важная папка для мониторинга.
    *   `/var/log` — системные логи и логи приложений (туда мы натравливаем Promtail, Fluentd или Logstash).
*   `/opt` — **Стороннее ПО**. Сюда часто устанавливают кастомные утилиты или проприетарный софт, который не идет в стандартном дистрибутиве.
*   `/home` и `/root` — **Домашние каталоги** пользователей и суперпользователя.
*   `/proc` и `/sys` — **Виртуальные файловые системы**. Они отражают состояние ядра и процессов в реальном времени.

### Основные правила для Git:
1.  **Не хранить секреты!** Все пароли, токены и приватные ключи должны быть добавлены в `.gitignore`.
2.  **Разделять окружения.** Конфиги для `dev` (тестового) и `prod` (продового) стендов должны лежать в разных подкаталогах.
3.  **Модульность.** Разбивайте конфигурации (например, Terraform или Ansible) на логические блоки, а не пишите всё в один файл.

# Права доступа
Когда вы вводите команду `ls -l`, вы видите список файлов и права доступа к ним. Права делятся на три группы:
*   **u** (User / Owner) — Владелец файла (обычно тот, кто его создал).
*   **g** (Group) — Группа пользователей, у которой есть общий доступ.
*   **o** (Others) — Все остальные пользователи в системе.

## 2. Типы прав (Буквенный и Цифровой вид)
Каждое право можно представить в виде буквы или цифры. Цифровой (восьмеричный) формат используется в DevOps чаще всего (например, при настройке прав в Docker или Ansible).

| Действие | Буква | Цифра | Что значит для файла | Что значит для каталога (папки) |
| :--- | :---: | :---: | :--- | :--- |
| **Read** (Чтение) | `r` | **4** | Можно смотреть содержимое | Можно увидеть список файлов (команда `ls`) |
| **Write** (Запись) | `w` | **2** | Можно изменять/удалять | Можно создавать, удалять и переименовывать файлы внутри |
| **Execute** (Выполнение) | `x` | **1** | Можно запускать как программу/скрипт | Можно зайти внутрь папки (команда `cd`) |

### Как складываются цифры?
Чтобы задать полные права группе, цифры складываются:
*   `r` + `w` + `x` = 4 + 2 + 1 = **7** (Полные права)
*   `r` + `w` = 4 + 2 = **6** (Чтение и запись)
*   `r` + `x` = 4 + 1 = **5** (Чтение и выполнение)

Пример: Магическое число **755** означает:
*   Владелец: `7` (читать, писать, запускать)
*   Группа: `5` (читать, запускать)
*   Остальные: `5` (читать, запускать)

## 3. Золотой стандарт
В реальных проектах (в Dockerfile, Ansible-плейбуках или при настройке CI/CD-раннеров) принято использовать принцип **наименьших привилегий**:

*   **`644` (`-rw-r--r--`)** — Стандарт для **обычных конфигурационных файлов** (например, `nginx.conf`). Владелец может править, остальные — только читать.
*   **`755` (`-rwxr-xr-x`)** — Стандарт для **скриптов автоматизации** (bash, python) и **каталогов**. Скрипт можно запустить, а в каталог можно войти.
*   **`600` (`-rw-------`)** — Стандарт для **секретов и ключей** (например, приватный SSH-ключ `id_rsa`). Доступ имеет *только* владелец. Если оставить права шире, SSH просто откажется работать из соображений безопасности.

## 4. Главные команды для работы с правами

*   `chmod 755 script.sh` — Изменить права доступа (Change Mode) для файла.
*   `chmod -R 755 /var/www` — Изменить права **рекурсивно** (`-R`) для всей папки и всего, что внутри нее.
*   `chown root:www-data config.json` — Изменить владельца и группу (Change Owner). В данном примере владелец — `root`, группа — `www-data`.

# SSH 
SSH сетевой протокол прикладного уровня для удаленного управления операционной системой и тунелирования TCP соединений 

### Основные команды для работы 

* __`ssh-keygen`__ - создание ключа
1.  **ED25519** (`ssh-keygen -t ed25519`) — **Современный стандарт и лучший выбор**. Он быстрее, намного безопаснее и генерирует очень компактные ключи. 
2.  **RSA** (`ssh-keygen -t rsa -b 4096`) — Классический алгоритм. Сейчас считается безопасным только при длине ключа **4096 бит** (задается флагом `-b`). Старые ключи RSA (1024 или 2048 бит) уже взламываются или не принимаются современными серверами.

* __`ssh-keygen -t (rsa,ed25519) -C "Комментарий (Ключ к серверу ...)"`__ - создание ключа

* __`ssh-copy-id user@server`__
Копирование открытый ключ на сервер

* __`ssh user@server`__
Подключение к серверу без запрашивания пароля после выполнение команды __`ssh-copy-id`__

### Копирование файлов через SSH, команда scp
__`-r`__ (позволяет копировать целые папки)
__`scp <опции> user1@server2:<путь до файла> user2@server2:<путь до файла>`__
Доп примеры:
* __`scp user@srver:/tmp1.txt /home/user`__
Копирование себе на машину
* __`scp /home/artem/123.txt user@server:/tmp`__
Копирование с машины на сервер

## Настройка политики по умолчанию:
В начале работы необходимо указать политику по умолчанию. По умолчанию будем все входящие пакеты отклонять:
```bash

```

```bash

sudo ufw allow OpenSSH
# или
sudo ufw allow 22/tcp
```
### Команды для выполнения действий с утилитой UFW

*   **enable** - включить фаерволл и добавить его в автозагрузку;
*   **disable** - отключить фаерволл и удалить его из автозагрузки;
*   **reload** - перезагрузить файрвол;
*   **default** - задать политику по умолчанию, доступно allow, deny и reject, а также три вида трафика - incoming, outgoing или routed;
*   **logging** - включить журналирование или изменить уровень подробности;
*   **reset** - сбросить все настройки до состояния по умолчанию;
*   **status** - посмотреть состояние фаервола;
*   **show** - посмотреть один из отчётов о работе;
*   **allow** - добавить разрешающее правило;
*   **deny** - добавить запрещающее правило;
*   **reject** - добавить отбрасывающее правило;
*   **limit** - добавить лимитирующее правило;
*   **delete** - удалить правило;
*   **insert** - вставить правило.

# firewalld используется в centos

## Синтаксис:
`firewall-cmd <опции> <зона> <правило>`

## Открыть порт 22
*(Примечание: в примерах команд на слайде указан порт 80 и служба ssh, заменяющие порт 22)*

```bash
firewall-cmd --permanent --add-port=22/tcp
firewall-cmd --permanent --zone=external --add-port=22/tcp
firewall-cmd --permanent --add-port=ssh
```
### Предустановленные зоны в Firewalld

Разработчики создали несколько предустановленных зон:

*   **drop** - блокировать все входящие пакеты, разрешить только исходящие;
*   **block** - в отличие от предыдущего варианта отправителю пакета будет отправлено сообщение по блокировке его пакета;
*   **public** - поддерживаются входящие соединения только для ssh и dhclient;
*   **external** - поддерживает NAT для скрытия внутренней сети;
*   **internal** - разрешены сервисы ssh, samba, mdns и dhcp;
*   **dmz** - используется для изолированных серверов, у которых нет доступа к сети. Разрешено только подключение по SSH;
*   **work** - разрешены сервисы ssh и dhcp;
*   **home** - аналогично internal;
*   **trusted** - всё разрешено.
